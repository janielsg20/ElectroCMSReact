# ElectroCMS Editor Design System — MASTER

## Purpose
This document is the visual and interaction source of truth for the ElectroCMS **editor chrome**. It does not define frontend or backend themes generated by projects.

ElectroCMS is a professional local-first no-code/low-code builder. The editor prioritizes speed, spatial clarity, information density, predictable manipulation, accessibility and confidence while editing.

## Unified visual direction
ElectroCMS uses **one editor UI/UX theme**: **Bento High Density**.

There are no selectable editor visual presets. `light`, `dark` and `auto` are appearance modes of the same design system, not separate themes. Frontend/backend project themes remain independent because they describe the generated project, not the ElectroCMS authoring environment.

### Product archetype
The unified language combines:
1. **Professional no-code builder** — canvas-first authoring and contextual inspection.
2. **Bento Grid workspace** — compact modular zones with clear grouping and hierarchy.
3. **High-density productivity tool** — maximum useful information without reducing readability.
4. **Design-system tooling** — consistent tokens, icons, states and semantics.
5. **Accessible responsive application** — keyboard, touch, contrast and reduced-motion support are first-class.

### Visual character
Use:
- compact modular panels with 6–8px inter-panel gaps;
- 10–14px working-surface radii;
- subtle elevation rather than decorative glass effects;
- dark graphite navigation chrome and neutral authoring surfaces;
- a restrained teal/accent role for selected, focused and actionable states;
- dense typography that remains readable;
- iconography for every primary navigation/menu action;
- micro-motion that explains hover, pressed, selected, opened and closed states.

Avoid:
- theme/preset selectors for the editor chrome;
- decorative animated gradients behind working data;
- large marketing whitespace;
- heavy glassmorphism across permanent surfaces;
- hidden hover-only functionality;
- motion that shifts DnD geometry;
- different interaction architecture between light and dark appearance.

## Design intelligence sources
ElectroCMS applies relevant practices from its React/UI skills and the established project architecture:
- component composition over monolithic UI files;
- semantic tokens instead of raw per-component colors;
- transform/opacity motion where possible;
- no unnecessary React rerenders for transient canvas interaction;
- explicit focus, pressed, selected, disabled, loading and error states;
- responsive layouts designed as product behavior, not a late CSS patch.

Do not copy third-party implementation code blindly and do not introduce a parallel UI architecture.

## No-code builder anatomy
Wide desktop authoring uses a stable four-zone model:
1. **Global header** — project/save state, document, breakpoint, zoom, history, preview/publish and appearance mode.
2. **Studio navigation** — workspaces/modules, always iconified and optionally labeled.
3. **Central authoring area** — insert library + dominant visual canvas.
4. **Context inspector** — properties/styles/responsive controls for current selection.

Rules:
- canvas receives the largest flexible area;
- navigation, library, canvas/editor and inspector read as related Bento modules;
- common property edits stay in the inspector;
- selection stays obvious while inspecting;
- layers/hierarchy are discoverable without internal IDs;
- structural actions are reversible through canonical commands;
- DOM remains renderer output, never source of truth.

## Bento layout contract
Use an 4px micro-grid and 8px primary rhythm.

Recommended shell values:
- panel gap: 6–8px;
- panel padding: 8–12px;
- dense row/control: 28–32px desktop;
- primary header: 52–56px;
- navigation rail: resizable within existing workspace preference limits;
- inspector: approximately 276–304px on wide layouts;
- mobile/touch critical targets: at least 44×44px.

Bento density means grouping related tools into compact modules. It must not turn every row into a card. Use bordered/elevated surfaces for major functional zones, then flatter internal rows for scan speed.

## Token architecture
Visual values follow:

```text
Primitive token
    ↓
Semantic token
    ↓
Component/Bento token
```

Components consume semantic/component tokens. The unified Bento layer may override radius, shadow, spacing and motion tokens but must not change canonical behavior.

Core semantic roles include:
- application background;
- working surface;
- subtle/muted surface;
- border;
- strong/muted text;
- accent/accent-soft;
- chrome/chrome-raised;
- success/warning/danger;
- focus ring;
- panel/floating elevation.

## Iconography
Every primary menu/workspace/module action uses the shared `Icon` system.

Rules:
- icons never replace accessible names;
- icon-only actions require `aria-label` and usually `title` where helpful;
- selected navigation retains icon + structural indicator, not color alone;
- hover motion may translate/scale icons subtly;
- pressed motion may compress icons/buttons;
- settings/open-state icons may rotate subtly;
- reduced-motion removes nonessential animation;
- icon animation must not change layout dimensions.

## Interaction states
Every interactive primitive defines relevant states explicitly:
- default;
- hover on hover-capable devices;
- focus-visible;
- active/pressed;
- selected/current;
- disabled;
- loading/saving;
- error;
- drag source;
- valid/invalid drop target;
- locked;
- hidden.

Color cannot be the only status signal.

## Motion system
Motion explains state changes; it does not decorate the workspace.

Targets:
- hover/press/icon feedback: 80–140ms;
- selected/open-state feedback: 120–200ms;
- drawer/popover reveal: 160–220ms;
- DnD insertion feedback: immediate;
- use transform/opacity when practical;
- do not animate precision hit-area geometry;
- honor `prefers-reduced-motion` globally.

## Navigation
The Studio rail is a primary professional tool surface.

Required behavior:
- icons on every primary workspace and Studio module;
- optional labels remain controlled by workspace display preference;
- current destination has persistent structural indication;
- resize remains keyboard and pointer accessible;
- compact layouts use an accessible drawer;
- the drawer enters with restrained motion and does not cause root overflow;
- navigation position preference remains independent from project data.

## Header
The header is a compact Bento command surface.

Priorities:
1. project + local save state;
2. active document;
3. responsive breakpoint;
4. zoom;
5. undo/redo;
6. preview/publish;
7. light/dark/auto appearance.

The old editor preset selector is removed. Appearance mode must not imply a different UI architecture.

## Element library
The insert library is a dense discovery surface.

Rules:
- search first;
- category filtering stays visible;
- element groups retain iconography;
- element tiles use compact Bento cells with clear hover/focus/pressed states;
- tablet/mobile may turn the library into a horizontal strip rather than consuming canvas width;
- no fake enabled capability.

## Canvas
Canvas compatibility is a first-class requirement.

Rules:
- canvas remains the dominant working surface;
- workspace around the document is visually distinct from project content;
- document boundary remains obvious at every supported zoom;
- canvas scrolling is locally contained with no document-root horizontal overflow;
- nested canvas scrolling uses `overscroll-behavior` intentionally;
- the scaled document keeps a stable top-center transform origin;
- canvas stage padding shrinks progressively across tablet/mobile;
- inspector moves below canvas on narrow layouts;
- critical commands remain reachable on touch layouts;
- browser zoom stays enabled;
- grid/guides/snapping remain transient overlays only.

### Drag and drop
- source gets immediate feedback;
- valid insertion areas are visible during drag;
- nesting vs sibling insertion is distinguishable;
- hit areas remain geometrically stable during native drag;
- transient paint may use `data-*` state;
- structural mutations go through canonical move commands;
- DOM order is never the structural source of truth.

## Inspector
The inspector is contextual and schema-driven.

Rules:
- persistent right dock on wide desktop;
- lower dock on narrow layouts;
- content/style tabs retain visible selected state;
- long sections use accessible disclosures;
- labels remain visible;
- validation is adjacent to the affected control;
- responsive inheritance state remains explicit;
- edits execute validated reversible canonical commands;
- touch layouts preserve a practical visible canvas area rather than allowing the inspector to consume the full screen.

## Typography
- neutral system/sans UI family;
- normal readable labels/body should remain at least 11–12px where practical;
- 10px is reserved for metadata/secondary labels;
- hierarchy comes from weight, contrast and spacing;
- numeric geometry uses tabular numerals;
- no expressive marketing typography in editor chrome.

## Accessibility
Baseline:
- WCAG AA contrast minimum;
- visible `:focus-visible` on every keyboard-operable control;
- keyboard path for primary commands;
- ARIA labels for icon-only buttons;
- semantic labels for inputs/selects;
- no hover-only functionality;
- browser zoom remains available;
- root document does not horizontally overflow;
- touch targets expand to at least 44px on mobile;
- `prefers-reduced-motion` is honored;
- `prefers-contrast: more` receives stronger boundaries;
- status uses text/icon/shape in addition to color.

## Responsive behavior
Editor responsiveness is separate from generated-site breakpoints.

### Wide desktop
- persistent rail + insert library + canvas + inspector;
- dense controls;
- maximum information visibility.

### Laptop / small desktop
- preserve the same zones with reduced widths;
- progressively hide low-priority geometry groups before core actions.

### Tablet
- Studio rail becomes drawer when compact shell activates;
- insert library becomes a horizontal Bento strip;
- inspector moves below canvas;
- canvas remains scrollable and visibly dominant.

### Mobile
- optimize for inspect/edit workflows rather than pretending desktop width exists;
- 44px critical targets;
- locally scrollable command bars;
- compact horizontal library;
- bottom inspector with bounded viewport height;
- locally contained canvas pan/scroll;
- no root overflow.

## Project theme separation
The following remain distinct:
1. **Unified editor UI** — Bento High Density only.
2. **Editor appearance** — light/dark/auto workspace preference.
3. **Project frontend/backend themes** — project-level definitions/IDs used by authored outputs.

Never allow the editor appearance or Bento chrome to mutate generated project themes.

## Quality checklist for every editor UI change
Before marking UI work complete:
- [ ] One Bento High Density visual language is used; no alternate editor preset UI exists.
- [ ] Primary task is obvious without tutorial text.
- [ ] Primary menus/actions use consistent iconography and accessible names.
- [ ] Hover, focus, pressed, selected and disabled states are explicit.
- [ ] Motion explains state and respects reduced motion.
- [ ] Keyboard path exists for primary controls.
- [ ] No control is hover-only.
- [ ] Selection/drag/drop state is explicit.
- [ ] Dense layout does not create root overflow.
- [ ] Mobile/touch critical targets expand appropriately.
- [ ] Canvas remains practically usable on desktop, tablet and mobile.
- [ ] Light and dark appearance remain readable without changing architecture.
- [ ] Component color/spacing/elevation uses tokens where practical.
- [ ] No fake functionality or misleading enabled controls.
- [ ] Canonical/unit/E2E/build quality gates remain green.
