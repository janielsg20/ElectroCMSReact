# ElectroCMS Editor Design System — MASTER

## Purpose
This document is the visual and interaction source of truth for the ElectroCMS **editor chrome**. It does not define frontend or backend themes generated by projects.

ElectroCMS is a professional local-first no-code/low-code builder. The editor must prioritize speed, spatial clarity, information density, predictable manipulation, accessibility, and confidence while editing.

## Design intelligence sources
The rules below are an ElectroCMS-specific synthesis of the public `nextlevelbuilder/ui-ux-pro-max-skill` repository (reviewed from `main` in August 2026), especially:
- `ui-ux-pro-max`: UX priority rules, product/style reasoning, React guidance.
- `design-system`: primitive → semantic → component token architecture.
- `ui-styling`: composable React UI, responsive behavior, accessibility, dark mode, and interaction patterns.

Do not copy third-party implementation code blindly. Adapt principles to ElectroCMS architecture and current React/CSS stack.

## Product archetype
ElectroCMS combines three product archetypes:
1. **Productivity Tool** — speed, clear hierarchy, functional color, micro-interactions.
2. **Design System / Component Library** — developer-first consistency, code-like structure, accessible semantics.
3. **Data-Dense SaaS / professional dashboard** — compact panels, maximum useful information, predictable grids.

### Primary visual direction
Use this blend as the default editor language:
- Minimalism / Swiss clarity.
- Flat functional surfaces.
- Data-dense professional layout.
- Accessible & ethical interaction design.
- Small contextual micro-interactions.

### Secondary effects
Use only where they improve hierarchy:
- Soft depth for floating menus, inspector overlays, command palettes, transient popovers.
- Light glass/translucency only for temporary overlays when contrast remains compliant.

### Avoid as editor defaults
Do not make these the base language of the editor:
- heavy glassmorphism across content surfaces;
- Aurora/animated gradients behind working data;
- 3D/hyperreal effects;
- decorative motion;
- skeuomorphic controls;
- large marketing-style whitespace;
- visual novelty that reduces scan speed.

Individual editor presets may reinterpret shape/color/elevation, but they must preserve this interaction architecture and information density.

## No-code builder anatomy
Desktop authoring is organized around a stable four-zone model:
1. **Top command/header bar** — project state, document, breakpoint, zoom, history, preview/export.
2. **Left insert/library zone** — primary catalog for elements, widgets, structures and reusable blocks, plus secondary workspace/layer navigation where appropriate.
3. **Central canvas** — dominant working surface and primary spatial context.
4. **Right contextual inspector** — properties/styles/responsive controls for current selection.

This interaction model should feel immediately familiar to users of professional visual page builders such as Elementor, while keeping ElectroCMS visual identity, terminology, architecture and implementation original.

### Insert / Elements Library contract
The left builder panel is a first-class authoring surface, not a generic navigation sidebar.

Required behavior as the relevant phases are implemented:
- searchable catalog of elements/widgets;
- category/group navigation;
- compact visual rows or tiles with recognizable icon + label;
- click-to-insert and drag-to-canvas insertion paths where structurally valid;
- clear disabled/modeled state when a component contract exists but runtime behavior is not ready;
- recently used/favorites when the library becomes large enough to justify them;
- reusable blocks/templates exposed through the same discoverable insertion mental model;
- optional panel modes/tabs for **Elements**, **Layers/Navigator**, **Templates/Blocks** and context-specific resources without replacing the central canvas;
- insertion always produces canonical nodes/data through registries/factories; the panel never mutates the DOM as state.

Rules:
- Canvas always receives the largest flexible area.
- The insert library remains visible/persistent on desktop whenever space permits; collapse it before removing access on smaller layouts.
- Common property edits stay in the right inspector; avoid modal dialogs for routine edits.
- Selection must remain visually obvious while inspecting.
- Layers, hierarchy and nesting must be inferable without reading internal IDs.
- Structural actions must be reversible with Undo/Redo.
- Never make the DOM the source of truth; editor visuals project the canonical model.
- Do not redesign ElectroCMS as a collection of dashboard cards when the primary task is visual composition; builder anatomy takes precedence.

## Density scale
Use an 4px base micro-grid and an 8px primary rhythm.

Recommended editor spacing:
- 4px — tight icon/control internals.
- 8px — standard dense gaps.
- 12px — panel padding / grouped controls.
- 16px — section separation.
- 24px — major visual group separation.

Recommended sizes:
- desktop dense toolbar/control height: 28–32px;
- standard compact row: 32–36px;
- primary editor header: roughly 48–56px where layout permits;
- inspector/sidebar reference width: roughly 240–320px, responsive and resizable when implemented;
- mobile/touch critical targets: at least 44×44px.

Desktop may use compact 28–32px controls because this is a professional high-density authoring tool, but every action must retain keyboard access, visible focus, and sufficient pointer hit area. On touch layouts, expand critical targets to 44px.

## Three-layer tokens
All visual theming must follow:

```text
Primitive token
    ↓
Semantic token
    ↓
Component token
```

Examples:
```css
--blue-600: ...;                 /* primitive */
--accent: var(--blue-600);       /* semantic */
--canvas-selection-border: var(--accent); /* component */
```

Rules:
- Components consume semantic/component tokens, not raw theme colors.
- Editor theme presets modify token values, not component behavior.
- Frontend/backend project themes never alter editor tokens.
- Prefer tokenized spacing, radius, elevation, typography and motion in addition to color.

## Interaction states
Every interactive editor primitive must define the relevant states explicitly:
- default;
- hover (pointer devices only);
- focus-visible;
- active/pressed;
- selected;
- disabled;
- loading/saving;
- error;
- drag source;
- valid drop target;
- invalid drop target (when validation can be known before drop);
- locked;
- hidden.

Color alone must not be the only indicator for destructive/error/locked/hidden states.

## Drag and drop
DnD is a core no-code-builder interaction and must be treated as a first-class system.

Required behavior:
- source receives immediate visual feedback;
- insertion targets become physically large and visually discoverable during drag;
- target indicator communicates exact insertion position;
- nesting vs sibling insertion must be distinguishable;
- invalid structural moves are rejected by the canonical move engine;
- drag never mutates DOM order directly;
- keyboard-accessible alternatives remain available through structural commands as the editor evolves;
- drop zones must not rely on hover-only styling to become usable.

## Inspector behavior
- Inspector is contextual to selection and never a second source of project state.
- Generated controls come from widget schemas.
- Use progressive disclosure for advanced groups.
- Keep labels visible; placeholder-only fields are forbidden.
- Validation appears near the affected control.
- Responsive inheritance state must be visible and understandable.
- Routine changes execute reversible canonical commands.

Suggested section order when applicable:
1. Content / data
2. Layout
3. Size & position
4. Typography
5. Color & surface
6. Border & effects
7. Responsive
8. Advanced / visibility / accessibility

## Typography
The editor prioritizes scan speed over expressive typography.
- Use a neutral system/sans UI family.
- Keep hierarchy primarily through weight, contrast and spacing.
- Avoid body/label text below 12px for normal reading; micro labels may be smaller only when redundant and never the sole accessible label.
- Numeric geometry values use tabular numerals.
- Avoid more than two font families in editor chrome.

## Accessibility
Baseline:
- WCAG AA contrast minimum; target stronger contrast for critical working text.
- Visible `:focus-visible` treatment on all keyboard-operable controls.
- Full keyboard operation for primary editor commands.
- ARIA labels for icon-only controls.
- Semantic labels for inputs and selects.
- No hover-only functionality.
- Do not disable browser zoom.
- Respect `prefers-reduced-motion`.
- Status must use text/icon/shape in addition to color.

## Motion
Motion explains state changes; it does not decorate the workspace.
- micro feedback: ~80–120ms;
- common surface/state transitions: ~120–200ms;
- larger panel transitions: up to ~250ms when needed;
- animate transform/opacity when possible;
- avoid animating layout dimensions during precision DnD;
- reduced-motion mode removes nonessential transitions.

## Responsive editor
Editor responsiveness and generated-site breakpoints are separate systems.

Desktop:
- full multi-panel no-code workflow;
- dense controls;
- persistent insert library + canvas + contextual inspector when space permits;
- canvas remains dominant even with both side panels open.

Tablet:
- collapse secondary chrome before removing functionality;
- drawers/sheets can replace persistent sidebars;
- preserve insert-library, canvas actions and inspector access.

Mobile:
- prioritize inspect/edit workflows rather than pretending a desktop canvas fits unchanged;
- insert library and inspector may become drawers/sheets, but must remain reachable;
- critical touch targets ≥44px;
- local horizontal scrolling is permitted for dense toolbars when contained;
- root document must not overflow horizontally.

## Theme preset contract
Editor presets may change:
- color primitives/semantic tokens;
- surface elevation;
- border radius;
- typography emphasis;
- icon treatment;
- density within supported bounds;
- panel/card composition.

Editor presets may not change:
- canonical project data;
- widget behavior;
- undo semantics;
- accessibility names;
- route architecture;
- DOM-as-projection invariant;
- required editor functions.

## Quality checklist for every editor UI microphase
Before marking a UI microphase DONE:
- [ ] Primary task is obvious without tutorial text.
- [ ] Builder-style tasks expose insertion/discovery through the left library rather than burying components in settings.
- [ ] Keyboard path exists for primary controls.
- [ ] Focus treatment is visible.
- [ ] No control is hover-only.
- [ ] Selection/drag/drop state is visually explicit.
- [ ] Dense layout does not create root overflow.
- [ ] Mobile/touch critical targets expand appropriately.
- [ ] Light and dark appearance remain readable.
- [ ] Reduced motion is respected.
- [ ] Component colors/spacing use tokens where practical.
- [ ] No fake functionality or misleading enabled controls.
- [ ] Existing canonical/unit/E2E gates remain green.
